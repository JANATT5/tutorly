# How Tutorly's backend and AI features actually work

A study guide, not a reference card (that's `docs/API_GUIDE.md`, which this
document assumes and builds on). Read this top to bottom once — it walks
through one real request at a time, with the actual code, so you can see
*why* each file exists and how it connects to its neighbors. Every file
created or changed while building the AI features is covered somewhere
below; Part 4 is a flat index if you just need to jump to one.

---

## Part 0 — the shape of the whole app, in one picture

```
Prisma schema  →  API route  →  React hook  →  Page / component
prisma/schema.prisma   src/app/api/<resource>/route.ts   src/hooks/use<Resource>.ts   src/app/**, src/components/**
```

Every screen in this app gets its data the same way: a page calls a hook,
the hook calls a small Axios wrapper, that wrapper hits a Next.js API
route, the route talks to Postgres through Prisma, and the answer flows
back up through the exact same pipe. The AI features (chat, career quiz,
Planr roadmap) are **not a different architecture** — they're the same
four layers, with one extra hop in the middle: the API route talks to a
local AI model (via Ollama) *in addition to* Prisma, instead of only
Prisma. Once you understand the plain version below, the AI version is
just "one more thing the route does before replying."

## Part 1 — the plain (non-AI) flow, traced through one real request

Take "the browse page loads and shows a list of tutors." Here's every file
involved, in the order the request actually travels.

### 1. The page asks a hook for data

```tsx
// somewhere in a page/component
const { data: tutors } = useTutors({ subject: "Mathematics" });
```

### 2. The hook is generated by a factory, not hand-written

[`src/hooks/useTutors.ts`](../src/hooks/useTutors.ts) doesn't implement
`useTutors` itself — it calls
[`src/hooks/createResourceHooks.ts`](../src/hooks/createResourceHooks.ts)
once, which hands back a matched set of `useList / useOne / useCreate /
useUpdate / usePatch / useDelete` for that one resource:

```ts
export const {
  useList: useTutors,       // GET  /api/tutors
  useOne: useTutor,         // GET  /api/tutors/:id
  useCreate: useCreateTutor,   // POST /api/tutors
  useUpdate: useUpdateTutor,   // PUT  /api/tutors/:id
  usePatch: usePatchTutor,     // PATCH /api/tutors/:id
  useDelete: useDeleteTutor,   // DELETE /api/tutors/:id
} = createResourceHooks<Tutor, CreateTutorDto, TutorEditDto>({
  basePath: 'tutors',
  queryKey: 'tutors',
})
```

Every other resource (`useStudents`, `useBookings`, `useSubjects`, ...)
does the exact same thing with a different `basePath`. This is why adding
a whole new CRUD resource to this app is usually a ~20 line file, not a
few hundred: the list/create/update/delete plumbing is written once, in
`createResourceHooks.ts`, and reused. Under the hood each of those hooks
is just a `useQuery`/`useMutation` from `@tanstack/react-query` that calls
one of the Axios helpers below, and `useCreate`/`useUpdate`/`usePatch`/
`useDelete` all call `queryClient.invalidateQueries(...)` on success so
every screen showing that resource's list refetches automatically — you
never manually "refresh the list" after a mutation anywhere in this app.

### 3. The Axios layer normalizes success and failure

[`src/lib/axios.ts`](../src/lib/axios.ts) exports `axiosGet` / `axiosPost`
/ `axiosPut` / `axiosPatch` / `axiosDelete`. `useTutors` calls
`axiosGet<Tutor[]>('tutors?subject=Mathematics')`. This file's whole job is
turning "the server answered, but the answer might secretly be a failure"
into "either you get real data, or a thrown `ApiError`" — see the next
section for why that distinction exists. Every hook in the app goes
through one of these five functions; nothing calls `axios` or `fetch`
directly.

### 4. The route validates, queries Prisma, and replies through a fixed envelope

[`src/app/api/tutors/route.ts`](../src/app/api/tutors/route.ts):

```ts
export async function GET(request: NextRequest) {
  const subject = request.nextUrl.searchParams.get('subject')
  const tutors = await prisma.tutorProfile.findMany({
    where: { ...(subject ? { subjects: { some: { subject: { name: subject } } } } : {}) },
    include: tutorInclude,
  })
  return ok(tutors.map(withSessionsCount))
}
```

`ok()`, `created()`, `fail()`, and `handlePrismaError()` all live in
[`src/lib/apiResponse.ts`](../src/lib/apiResponse.ts). This is the single
most important convention in the whole backend, so it's worth stating
plainly:

> **Every route always replies with HTTP 200.** The *real* outcome —
> success, a validation error, a 404, a conflict — lives inside the JSON
> body's own `status` field: `{ status: number, message: string, data?: T }`.

Why: it means every route, no matter what kind of failure it hits, can be
handled the exact same way on the client, instead of every caller needing
its own switch statement over HTTP status codes. `axios.ts`'s `unwrap()`
is the piece that makes this actually useful — it reads that embedded
`status`, and if it's `>= 400`, throws an `ApiError` (defined in that same
file) instead of letting the caller think it got real data:

```ts
function unwrap<T>(data: IResponse<T>): IResponse<T> {
  if (data && typeof data.status === 'number' && data.status >= 400) {
    throw new ApiError(data.message ?? 'Request failed', data.status, data.data)
  }
  return data
}
```

So from the hook's point of view, a resolved promise always means real
success — no route ever has to be special-cased. `handlePrismaError()`
exists so every route doesn't repeat the same try/catch: it turns Prisma's
own error codes (`P2002` unique constraint, `P2025` not found, `P2003` bad
foreign key) into the right `fail(status, message)` call automatically.

### 5. Validation lives in its own schema file

[`src/app/api/schemas/tutors.schema.ts`](../src/app/api/schemas/tutors.schema.ts)
holds `createTutorSchema` and `tutorEditSchema` (zod). `route.ts` imports
and calls `.safeParse(body)` before touching the database — if it fails,
`fail(400, 'Invalid request', parsed.error.flatten())` goes straight back,
and Prisma never even sees the bad request. (These used to live inline as
`schema.ts` next to each `route.ts`; they were consolidated into
`src/app/api/schemas/` in a separate pass this session — same pattern,
just one folder instead of scattered co-located files.) One rule holds
across every resource's schema: whichever field says *who this row
belongs to* (`userId`, `tutorId`, `studentId`, ...) is only in the create
schema, never the edit schema — you can edit a tutor's bio, you can't
reassign whose profile it is.

### 6. `useCurrentUser` — the one hook nearly every page also calls

[`src/hooks/useCurrentUser.ts`](../src/hooks/useCurrentUser.ts) bridges
the fake login cookie (`src/lib/session.ts` — just a role + username
string, **not real authentication**) into actual database rows, by doing
a `useUsers({ username })` lookup and then, depending on role, a
`useStudents`/`useTutors` lookup scoped to that user's id:

```ts
const { data: users } = useUsers(username ? { username } : undefined, { enabled: Boolean(username) })
const user = users?.[0]
const { data: tutors } = useTutors(user ? { userId: user.id } : undefined, { enabled: role === 'tutor' && Boolean(user) })
```

This is why so many pages destructure `{ studentProfile, tutorProfile,
profileId }` from one hook instead of building their own lookup — and why
`docs/API_GUIDE.md` calls this out as a real, temporary bridge (a verified
server session should replace it before this app ever holds real user
data).

That's the entire non-AI backend. Every resource in the table in
`docs/API_GUIDE.md` follows exactly this shape. Once this is second
nature, the AI features below will look almost boring by comparison — same
shape, one extra hop.

## Part 2 — the AI architecture

### 2.1 The mental model: Ollama pretends to be OpenAI

All three AI features (chatbot, career quiz, Planr roadmap) talk to a
**local** LLM server called [Ollama](https://ollama.com), running on this
machine at `http://localhost:11434`. Ollama happens to implement the same
HTTP API shape as OpenAI's Chat Completions endpoint, so the official
`openai` npm package — normally used to call OpenAI's paid cloud API —
works against it completely unmodified. The only thing that changes is
where it points:

[`src/lib/ai/client.ts`](../src/lib/ai/client.ts) — the *only* place this
project constructs that client:

```ts
export const ai = new OpenAI({
  baseURL: process.env.OPENAI_BASE_URL ?? 'http://localhost:11434/v1',
  apiKey: process.env.OPENAI_API_KEY ?? 'ollama', // Ollama ignores this value
})
export const AI_MODEL = process.env.OPENAI_MODEL ?? 'llama3.2:3b'
```

Every AI route imports `ai` and `AI_MODEL` from this one file. That means
switching from free local Ollama to real paid OpenAI later is: set
`OPENAI_API_KEY` to a real key in `.env`, delete/comment out
`OPENAI_BASE_URL` — zero code changes anywhere else in the app. This is
also why the model is swappable: two models are pulled locally right now
(`llama3.2:3b`, the default — fast; `qwen3:4b` — slower but was the
original default), and switching between them is just `OPENAI_MODEL=` in
`.env`.

### 2.2 Two different problems need two different techniques

There are two fundamentally different things the AI needs to do here, and
each gets its own file:

| Need | Technique | File |
|---|---|---|
| "Have an open-ended conversation, but only state real facts" | **Tool-calling loop** — offer several tools, let the model decide if/which to call, possibly several rounds | `src/lib/ai/tools.ts` + `src/app/api/chat/route.ts` |
| "Give me back exactly this JSON shape, once" | **Forced single-tool call** — offer one tool whose *parameters* schema IS the shape wanted, force it to be called | `src/lib/ai/structuredCompletion.ts` + the two `api/ai/*` routes |

Both techniques are built on the same underlying mechanism (OpenAI/Ollama
"tool calling" — the model can request that a named function be called
with certain JSON arguments, instead of just returning text). The
difference is *why* tools are used: in the chatbot, tools are optional
lookups the model reaches for when it needs a fact. In the other two,
there's exactly one "tool," and it isn't really a tool at all — it's a
JSON-shape contract being smuggled through the tool-calling mechanism
because that's a much more reliable way to get structured JSON out of a
small model than just asking nicely in the prompt.

### 2.3 Why tool-calling at all, instead of just asking the model?

[`src/lib/ai/tools.ts`](../src/lib/ai/tools.ts) opens with the actual
reason:

> Why tools instead of just describing the data in the prompt: the model
> is much more prone to inventing plausible-sounding tutor names or prices
> than a frontier model would be. Forcing it to call these functions for
> anything data-shaped means every fact in its answer traces back to a
> real row, not a guess.

Concretely, this file exports four plain async functions that call Prisma
directly — no HTTP round-trip back into this app's own API, since this
code already runs server-side:

```ts
export async function searchTutors(args: { subject?: string; curriculum?: ...; maxHourlyRate?: number }) { ... }
export async function listSubjects() { ... }
export async function getTutorDetails(args: { tutorId: string }) { ... }
export async function searchPracticeQuestions(args: { subjectId?: string; difficulty?: string }) { ... }
```

...plus a JSON-schema `toolDefinitions` array (the model-facing
description of each function — its name, description, and parameter
shape) and a small `registry` + `executeTool(name, args)` dispatcher that
the chat route uses to actually run whichever tool the model asked for.

### 2.4 The chatbot: a real tool-calling loop

[`src/app/api/chat/route.ts`](../src/app/api/chat/route.ts) is the
clearest place to see the mechanism end to end. Simplified:

```ts
const messages = [{ role: 'system', content: SYSTEM_PROMPT }, ...parsed.data.messages]

for (let round = 0; round < MAX_TOOL_ROUNDS; round++) {
  const response = await ai.chat.completions.create({ model: AI_MODEL, messages, tools: toolDefinitions })
  const message = response.choices[0]?.message
  const toolCalls = message.tool_calls?.filter(c => c.type === 'function') ?? []

  if (toolCalls.length === 0) {
    return ok({ role: 'assistant', content: message.content ?? '' })   // done — final answer
  }

  messages.push(message)   // the model's tool-call request goes back into history
  for (const call of toolCalls) {
    const args = JSON.parse(call.function.arguments)
    const result = await executeTool(call.function.name, args)
    messages.push({ role: 'tool', tool_call_id: call.id, content: JSON.stringify(result) })
  }
  // loop again — the model now sees the tool result and can answer, or call another tool
}
```

Walk through a real example — a user asks *"Are there any Physics tutors
under $20/hr?"*:

1. **Round 1**: the model reads the question, decides it needs data, and
   replies not with text but with a tool call: `search_tutors({ subject:
   "Physics", maxHourlyRate: 20 })`. `toolCalls.length > 0`, so the loop
   doesn't return yet.
2. The route runs `executeTool('search_tutors', {...})`, which is really
   just `prisma.tutorProfile.findMany({ where: { verified: true, subjects:
   {...}, hourlyRate: { lte: 20 } } })` under the hood, trimmed down to the
   fields worth handing back.
3. That result gets pushed into `messages` as a `role: 'tool'` message,
   and the loop runs again.
4. **Round 2**: the model now has the real tutor rows in its context and
   replies in plain text, summarizing them. `toolCalls.length === 0` this
   time, so the route returns `{ role: 'assistant', content: "..." }`.

`MAX_TOOL_ROUNDS = 4` exists so a confused model asking for tool after
tool can't hang the request forever — after 4 rounds with no final text
answer, the route gives up honestly with a `fail(502, ...)` rather than
looping.

The system prompt is where "don't hallucinate" is actually enforced, not
just hoped for:

```
Rules:
- Only state facts that came back from a tool call (tutor names, prices, subjects, ratings, availability). Never invent or guess any of these.
- If a tool returns no results, say so plainly — don't make something up instead.
```

On the client side, [`src/components/chat/ChatWidget.tsx`](../src/components/chat/ChatWidget.tsx)
is a floating button + panel mounted once in
[`src/app/layout.tsx`](../src/app/layout.tsx) (so it's on every page),
holding the conversation only in local component state — refresh the page
and it's gone, which is a deliberate, documented limitation (a real
`ChatMessage`/`Conversation` Prisma model could persist it later, same
pattern as every other resource in Part 1). Every render of an assistant
message carries a small "AI" label, and the input is disabled with a
"Thinking… can take up to a minute" message while `isSending` is true.

### 2.5 Structured completion: forcing one exact JSON shape back

The career quiz and Planr roadmap don't want a conversation — they want
one specific object back (`{ paths: [...], subjectsToStrengthen: [...] }`,
or `{ title, courses: [...] }`). That's
[`src/lib/ai/structuredCompletion.ts`](../src/lib/ai/structuredCompletion.ts),
and it's the file with the most hard-won detail in the whole AI layer,
because getting a small local model to reliably return valid structured
JSON turned out to be the hardest part of this whole feature set. Three
things it does, in order:

**1. Force a single tool call.** A "tool" is defined whose *parameters*
JSON-schema literally *is* the shape being requested, and
`tool_choice: 'required'` forces the model to always respond by calling
it (instead of `tool_choice: 'auto'`, which lets it just answer in text —
tested directly and found much less reliable for this):

```ts
const tool: ChatCompletionTool = {
  type: 'function',
  function: { name: options.toolName, description: options.toolDescription, parameters: options.parameters },
}
const response = await ai.chat.completions.create({
  model: AI_MODEL,
  messages: [{ role: 'system', content: options.system }, { role: 'user', content: options.user }],
  tools: [tool],
  tool_choice: 'required',
})
```

**2. Repair a real, observed model quirk before validating.** Tested
directly against `llama3.2:3b`: for a schema with a nested array of
objects (like `courses: [...]`), the model reliably *does* call the tool,
but sometimes serializes that one property as a JSON **string** instead of
a native array — `{"courses": "[{...}]"}` instead of `{"courses":
[{...}]}`. `repairNestedJson()` walks the parsed arguments and
`JSON.parse()`s any string value that looks like a JSON array/object
before validation, recovering that common case:

```ts
function repairNestedJson(value: unknown): unknown {
  if (typeof value === 'string') {
    const looksLikeJson = /* starts with [ or {, ends with ] or } */
    if (!looksLikeJson) return value
    try { return repairNestedJson(JSON.parse(value.trim())) } catch { return value }
  }
  if (Array.isArray(value)) return value.map(repairNestedJson)
  if (value && typeof value === 'object') return /* same repair, recursively, on every value */
  return value
}
```

**3. Validate with zod, and retry up to 3 times total before giving up
honestly.** Even after the fix above, a small model forced into
`tool_choice: 'required'` doesn't succeed every single time — measured
directly, anywhere from ~65% to ~95% per attempt depending on how nested
the requested shape is. So `structuredCompletion()` (the exported
function) wraps the single-attempt version in a loop:

```ts
export async function structuredCompletion(options) {
  let lastError
  for (let attempt = 1; attempt <= 3; attempt++) {
    try { return await attemptStructuredCompletion(options) }
    catch (error) { lastError = error }
  }
  throw lastError   // 3 consecutive failures — a real, honest error, not a crash or a fake result
}
```

Each attempt is ~15-45s, so a worst-case triple failure is still bounded
(a couple of minutes), and it still ends in a real, catchable error rather
than silently retrying forever or returning something fabricated.

### 2.6 The two structured routes, and a real product decision that came out of debugging

[`src/app/api/ai/roadmap/route.ts`](../src/app/api/ai/roadmap/route.ts) is
the simpler of the two — validate the request with zod, build a short,
*imperative* system prompt ("Call return_roadmap with a 3-8 course
roadmap...", not a long explanation — a long explanatory prompt measurably
lowered how often the model actually used the tool call, tested directly),
call `structuredCompletion()`, return the result.

[`src/app/api/ai/career-recommendation/route.ts`](../src/app/api/ai/career-recommendation/route.ts)
has one extra, worth understanding: the requested shape originally nested
`subjectsToStrengthen: string[]` *inside each* recommended path (so:
array-of-objects, each containing another array). That turned out to be
the least reliable shape the model could return — measured as low as ~35%
success per attempt. The fix wasn't "add more retries and hope" — it was
noticing that `subjectsToStrengthen` isn't really a per-path idea anyway
(it's "here's what to work on," a whole-quiz-result concept), so it moved
to the top level of the response instead:

```ts
const responseSchema = z.object({
  paths: z.array(z.object({ title: z.string().min(1), description: z.string().min(1) })).min(1).max(3),
  subjectsToStrengthen: z.array(z.string()),   // flat, not nested inside each path
})
```

That's both a genuine reliability fix (flatter shapes are more reliable
for this model) *and* a better product shape — a rare case where the
debugging fix and the "right" design were the same change. It also means
[`src/app/quiz/page.tsx`](../src/app/quiz/page.tsx) no longer needs to
compute a union of subjects across paths on the client — it just reads
`response.data.subjectsToStrengthen` directly.

One more grounding step happens *after* the AI call, in both routes: real
subject names are fetched first (`listSubjects()`), and the model's
`subjectsToStrengthen` output is filtered against that real list before
the response ever reaches the client —

```ts
const realSubjectsLower = new Set(realSubjects.map(s => s.toLowerCase()))
const grounded = {
  paths: result.paths,
  subjectsToStrengthen: result.subjectsToStrengthen.filter(s => realSubjectsLower.has(s.toLowerCase())),
}
```

— because a small model can still ignore a "only use these exact names"
instruction in the prompt. The prompt instruction is the first line of
defense; this filter is the one that's actually trustworthy, the same
"grounding, not guessing" idea as the chatbot's tools, just applied as a
post-filter instead of a pre-fetch.

### 2.7 How the two AI-wired pages call these routes

[`src/app/quiz/page.tsx`](../src/app/quiz/page.tsx) — the 8-question quiz
UI itself didn't change; what changed is what happens when it finishes.
Answers are collected as plain option text, and a `useEffect` (guarded by
a `useRef`, not a second piece of state, specifically to fire exactly once
per finished attempt) calls the route and saves the result:

```ts
useEffect(() => {
  if (step !== "results" || hasGeneratedRef.current) return
  hasGeneratedRef.current = true
  async function generate() {
    const response = await axiosPost("ai/career-recommendation", {
      answers: careerQuizQuestions.map((q, i) => ({ prompt: q.prompt, answer: answers[i] })),
    })
    setTopPaths(response.data?.paths ?? [])
    setSubjectsToStrengthen(response.data?.subjectsToStrengthen ?? [])
    if (studentProfile) createQuizResult.mutate({ studentId: studentProfile.id, resultLabel: topPaths[0].title, answers })
  }
  generate()
}, [step])
```

[`src/app/planr/create-project/page.tsx`](../src/app/planr/create-project/page.tsx)
follows the same shape for step 3: collect a goal, a current level, and
per-subject self-rated skill (`"beginner" | "comfortable" | "confident"`),
call `POST /api/ai/roadmap`, store the result in
`generationState: "idle" | "generating" | "ready" | "error"`, and on
success save it via the already-existing `useCreatePlanrPath` — the exact
same resource-hook pattern from Part 1, just receiving an AI-generated
roadmap instead of a hand-typed one.

Both pages show a real loading state while the request is in flight and a
real "couldn't generate this, try again" state on failure — never a fake
instant result, matching the same "never fake it" convention as the rest
of this session's work.

## Part 3 — practice questions (not AI, but built in the same session)

[`prisma/seed-practice-questions.mjs`](../prisma/seed-practice-questions.mjs)
isn't part of the AI pipeline at all — it's a plain idempotent seed
script, the same category as `prisma/seed-demo-accounts.mjs` and
`prisma/seed-tutors.mjs`. It holds a flat array of 40 real, hand-written
questions (8 per subject × 5 subjects — Mathematics, Physics, Chemistry,
Biology, Computer Science — spread across Easy/Medium/Hard), and for each
one:

```js
const subject = await ensureSubject(item.subjectName)   // find-or-create the Subject row
const existing = await prisma.practiceQuestion.findFirst({ where: { subjectId: subject.id, question: item.question } })
if (existing) { skipped++; continue }
await prisma.practiceQuestion.create({ data: { subjectId: subject.id, ...item } })
```

Safe to re-run any time (`node prisma/seed-practice-questions.mjs`) —
already-seeded questions are skipped by exact text match, not duplicated.

## Part 5 — running and testing this yourself

1. **Ollama needs to be running** on this machine — `ollama serve` (or it
   may already be running as a background process; check with
   `ollama list`, which should show `llama3.2:3b` and `qwen3:4b`).
2. **No `.env` changes are required** to use the free local setup — it's
   the default when `OPENAI_API_KEY`/`OPENAI_BASE_URL`/`OPENAI_MODEL` are
   all unset.
3. **Test a route directly**, without the UI, to see the raw JSON:
   ```bash
   curl -s -X POST http://localhost:3000/api/chat \
   ```

   A correct answer here should list exactly the 5 real subjects from the

4. **Expect real latency.** Even on the faster model, a response is
   commonly 15-60 seconds — this is a genuine small local model, not a
   hosted GPT. The structured routes (career quiz, roadmap) can take
   longer in the worst case because of the internal retry loop. This is
   documented, not a bug to "fix" by itself.
5. **A `502` from an AI route is a real, designed outcome**, not
   necessarily a bug — it means the model failed to produce a valid
   result after 3 attempts (structured routes) or 4 tool-call rounds
   (chat). The UI always has a "try again" path for this.
